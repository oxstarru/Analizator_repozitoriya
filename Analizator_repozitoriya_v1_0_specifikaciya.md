# Спецификация утилиты «Анализатор репозитория → Markdown»

> **Назначение документа:** технический источник для понимания и будущей доработки существующей реализации. Составлен по исходному HTML версии 0.25, принятой для финализации в 1.0, и по результату пользовательской проверки. **Описывает фактически имеющиеся эвристики, а не желаемую идеальную архитектуру.** Документ внутренний; для публикации на блоге предназначен отдельный README.

### 1.1. Статус и предел ответственности

**Это финализация текущего этапа, не утверждение о полном решении исходной задачи.** Пользователь завершил разработку на v0.25, поскольку анализ репозитория перестал быть актуален для собственной работы, а полное тестирование на реальном проекте неосуществимо в доступных условиях.

Исходное ожидание: извлечь из большого репозитория **достоверную проектную документацию, которую можно положить в базу знаний**, включая цепочки вызовов до конкретных внутренних микросервисов. Полученная реализация **генерирует полезный первичный каркас документации**, но не полностью восстанавливает внутренние связи, бизнес-смысл и фактическое поведение сервиса. Ни пользовательская выборочная проверка, ни синтетические тесты не являются основанием объявлять документацию полностью проверенной.

**Результат пользовательского прогона v0.25:** 238 обнаруженных модулей, 482 контроллера, 1490 endpoints, 22754 Java-файла. По наблюдениям пользователя, охват дерева стал существенно ближе к реальному и страницы отдельных методов выглядят достаточно содержательно, но полнота по API/БД/Kafka не доказана. Сохранять эти числа только как свидетельство о конкретном тесте, а не как норматив производительности или гарантированную точность.

## 2. Решаемая задача и границы

### 2.1. Назначение

Превратить доступный локально исходный код многомодульного Java/Spring-репозитория в структурированный набор Markdown-страниц для навигации, первичного анализа, обсуждения с разработчиками и наполнения базы знаний проекта. Упор — на обозримую карту репозитория, REST API, модели входных/выходных данных и сигналы о технических зависимостях. Восстановление исполнения во время работы приложения не предусмотрено.

### 2.2. Что не является функцией

- Не компилирует, не запускает и не отлаживает Java-код.
- Не вызывает REST endpoints, брокеры, БД и внешние сервисы.
- Не подключает ИИ по API и не выполняет семантический AI-анализ (возможный отдельный этап развития).
- Не валидирует построенные REST-схемы по фактическим HTTP-запросам и ответам.
- Не выдаёт гарантированно полную карту всех микросервисов и межсервисных переходов.
- Не меняет исходные файлы; не записывает Markdown внутрь репозитория. Сохранение результата — через скачивание архива.

## 3. Пользовательский сценарий и интерфейс

1. **Выбрать папку** — кнопка вызывает `window.showDirectoryPicker({ mode: 'read' })`. При отсутствии API показывается предупреждение и кнопка отключается. Дополнительное необязательное поле — загрузка CSV/XLSX каталога БД.
2. **Выбрать микросервисы** — дерево модулей группируется по родительскому пути, показаны относительные пути, число найденных/выбранных. `Выбрать все` выбирает все позиции, `Снять все` действительно сбрасывает все. `stub/stop/стоп/заглуш/mock` выключаются по умолчанию, но доступны для ручного включения. Раскрываемая инвентаризация показывает ограничения обхода.
3. **Начать сканирование** — после выбора хотя бы одного модуля последовательно читаются конфиги, константы, Java-файлы и строятся индексы; интерфейс показывает прогресс и текущий файл.
4. **Что нашлось** — четыре счётчика: число выбранных модулей в результате, контроллеров, REST endpoints и Java-файлов. Выпадающий список предоставляет предпросмотр сводки, карты, диагностики, инвентаризации, индексов отдельных модулей, методов, БД, топиков, очередей, задач и шедулеров.
5. **Скачать архив** — опционально убрать исходники методов флажком `includeSource`, затем собрать и скачать ZIP. Флажок влияет и на предпросмотр отдельного метода.

**Состояние:** структура найденных модулей и результаты живут в памяти открытой страницы. Базы данных для хранения и пользовательского аккаунта нет. Повторное открытие папки сбрасывает предыдущее состояние анализа; перезапуск страницы не восстанавливает сканирование.

## 4. Входные форматы и допущения

### 4.1. Дерево репозитория

- Выбирается **каталог**, обычно корень всего репозитория; вложенность не обязана быть фиксированной (`root/app/...`, `root/facade/...`, `root/starter/...` и т. п.).
- Кандидат в модуль — директория, где одновременно есть **`pom.xml` либо `build.gradle`/`build.gradle.kts`**, а также **`src`** на том же уровне. Название такого кандидата в интерфейсе «микросервис» историческое: технически это *модуль* и может быть библиотекой/агрегатором с кодом, а не отдельным деплоем.
- При обнаружении модуля обход **продолжается по его дочерним папкам**, кроме `src`, чтобы не потерять вложенные модули. Для поиска модулей ограничение `DISCOVERY_MAX_DEPTH = 48`; о достижении границы создаётся предупреждение.
- Пропускаются каталоги `target`, `.git`, `.idea`, `node_modules`, `build`, `out`, `env`, `.mvn` и любые начинающиеся с точки.
- Папки с манифестом сборки без `src` не включаются в список модулей, но заносятся в инвентаризацию; это не обязательно ошибка (например, агрегатор).
- Ошибки чтения каталогов и превышения предела глубины в фазе обнаружения отображаются в интерфейсе и `_inventory.md`.

### 4.2. Java

- Для отобранного модуля считываются `.java` **только из `src/main/java/`**, не из тестов.
- При чтении исходников из `src` используются рекурсивный обход и предел глубины **48**; о превышении/ошибке создаётся предупреждение.
- Начиная с v0.25 Java-файлы дочерних модулей **не присоединяются повторно к родителю**: обход сборки Java в модуле на верхнем уровне входит только в его `src`.
- При предварительном сборе общих структур из репозитория ищутся типичные Java-файлы констант, DTO, моделей, репозиториев и клиентов. Это **эвристика по имени и пути**, а не индексация вообще всех Java-классов независимо от выбора.

### 4.3. Дополнительный каталог БД

- Необязательный одиночный `.csv` или `.xlsx`, читаемый локально. В реализации присутствует собственный CSV-парсер и разбор XML-частей XLSX через встроенный JSZip.
- Ожидаемые заголовки колонок: `Схема`, `Таблица`, `Описание таблицы`, `Поле`, `Тип`, `Описание поля`, `Обязательное`.
- Индексируются схемы, таблицы, поля и их описания; используются для уточнения схем/полей при генерации страницы БД и гипотез о маппинге DTO → БД.
- Старые бинарные `.xls` и другие варианты табличных структур не являются заявленным форматом; совпадение заголовков важно.

## 5. Последовательность работы алгоритма

### 5.1. Этап A — обнаружение модулей

`findMicroservices()` → рекурсивный `scanForPom()`:

1. Сбросить старый результат и создать объект `discovery`.
2. Обойти дерево сверху вниз, отслеживая каталог и относительные сегменты пути.
3. В каждом каталоге проверить наличие Maven/Gradle-манифеста и `src`.
4. Если оба признака есть — записать кандидата (`name`, `relPath`, `group`, `groupSegments`, `handle`) **и продолжить обход остальных дочерних папок**.
5. Если есть манифест, но нет `src` — записать `skippedWithoutSrc`.
6. Ошибки/глубину — в `discovery.errors`/`discovery.depthLimits`.
7. Отсортировать по группе и пути, выключить группы-заглушки, вывести список и сводную инвентаризацию.

**Главный исправленный дефект v0.23/v0.24:** ранее при `pom.xml + src` выполнялся `return`, что отбрасывало все дочерние Maven/Gradle-модули. Также ранее был более низкий предел глубины. В v0.25 возврат удалён, увеличен лимит и добавлена наблюдаемость обхода.

**Условие полноты:** даже 0 ошибок инвентаризации означает лишь, что обойдены доступные папки согласно критериям. Модули без манифеста, с нестандартной структурой исходников или глубже порога по-прежнему могут отсутствовать.

### 5.2. Этап B — чтение конфигурации

`gatherConfig(rootHandle, ..., 0)`:

- Обходит дерево репозитория до глубины **30**, кроме пропускаемых директорий и папки `test`.
- Читает `.properties`, `.yml`, `.yaml` (размер файла не более 1 МиБ).
- Разбирает простые `key=value` / `key:value` и YAML-карты по отступам в плоские ключи `a.b.c`. Списки, сложные YAML-якоря, мультистрочные значения поддерживаются только ограниченно или игнорируются.
- По самому длинному префиксу пути `configTargetFor()` относит конфиг к соответствующему модулю; остальное — в `sharedConfig`.
- Формирует эффективный `configMap` в виде `sharedConfig` + локальный конфиг модуля. Профильные значения имеют меньший приоритет при уже заполненном ключе.
- Не загружает конфигурацию работающего Spring-приложения из окружения, Config Server, Vault и т. п.; поэтому конечные значения могут отличаться от runtime.

### 5.3. Этап C — сбор констант и общих типов

`gatherConstantsTree()` проходит репозиторий до глубины **30** (за исключением `test` и пропускаемых папок), отбирает Java-файлы по типовым именам/папкам:

- константы маршрутов/API (`Constants`, `Paths`, `Url`, `Endpoint`, `Mapping`, `Route`, `Api`, пакеты `common`, `shared`, `config` и т. п.);
- DTO, модели, сущности, репозитории и мапперы по именам и пакетам;
- Feign/API-клиенты, адаптеры и прокси по именам и пакетам.

Для подходящих файлов размером до 1 МиБ вызывает `extractConstants()`, `registerClasses()`, `registerRepo()`, `registerMyBatisMapper()`, `registerFeign()`. По `static final String` строятся записи в `constMap` по короткому имени и `Class.CONST`; **конкатенация вычисляется упрощённо** (строковые литералы). Константы сложных выражений могут быть интерпретированы неверно; короткие имена могут конфликтовать.

### 5.4. Этап D — чтение выбранных Java-модулей

Для каждого выбранного модуля:

1. `readPomDescription()` читает `<description>` из `pom.xml`, при отсутствии — первую содержательную строку локального README (либо позднее `configInfoDesc()` из конфигурации).
2. `collectJavaFiles()` собирает `src/main/java/**/*.java` с защитой от вложенных дочерних модулей и от ошибок чтения.
3. Для каждого Java-файла последовательно вызываются:
   - `recordDeclaredClasses` — перепись коротких имён Java-классов для диагностики коллизий;
   - `extractConstants` — константы;
   - `registerClasses` — DTO, enums, JPA-сущности;
   - `registerFeign` — `@FeignClient`;
   - `registerRepo` — JPA-репозитории и `@Query`;
   - `registerMyBatisMapper` — аннотационные SQL-мапперы;
   - `indexClassMethods` — поля и тела методов классов;
   - `parseJavaFile` — REST-контроллеры и методы;
   - `collectMessaging` — Kafka/JMS и шедулеры `@Scheduled`;
   - `collectDiagnostics` — перепись распознанных/нераспознанных маркеров;
   - `registerQuartzConfig`, `collectQuartzJobs` — Quartz;
   - `collectTaskSignals` — признаки отложенных задач.
4. Ошибки конкретного файла записываются в `scanWarnings`: по ошибке отдельного файла не срывается весь обход.
5. Каждые 25 файлов делается короткая уступка управления интерфейсу (`setTimeout(..., 0)`) для обновления прогресса.

**Замечание:** большинство индексов (`classRegistry`, `methodIndex`, `feignRegistry`, `entityRegistry` и пр.) глобальны в рамках одного запуска и нередко адресуются **коротким именем класса**, без полного Java package. При одинаковых названиях из разных модулей/пакетов индекс может содержать не тот класс. `ambiguousJavaClasses()` сообщает о таких совпадениях, но **не исправляет семантику связывания**.

### 5.5. Этап E — разрешение и агрегация

- `resolveAllPaths(selected)` подставляет значения переменных из конфигов и Java-констант в пути Spring-методов; фиксирует счётчики и неразрешённые имена.
- `resolveAllMessaging(selected)` собирает каналы сообщений и агрегирует роли издатель/подписчик.
- `buildTaskFeatures(ms)` группирует эвристические сигналы отложенных задач по смысловым фичам.
- Результат сохраняется в `scanResult`, после чего доступны просмотр и экспорт.

### 5.6. Этап F — формирование Markdown/ZIP

Генерация выполняется функциями `generateOverview`, `generateDiscoveryReport`, `generateDiagnosticsFile`, `generateRepoMap`, `generateMicroserviceIndex`, `generateDatabaseFile`, `generateMethodFile`, `generateChannelFile`, `generateSchedulerFile`, `generateTaskFile`.

Экспорт через **JSZip**, `zip.generateAsync({type:'blob'})`, скачивание по Blob URL. Путь модуля в архиве строится из иерархии `groupSegments + name` с очисткой сегментов; совпавшим итоговым путям добавляется суффикс. URL освобождается с задержкой, чтобы не прерывать скачивание в Firefox/Safari (при том что выбор папки в этих браузерах может быть недоступен).

## 6. Детекторы: что именно умеют и на чём основаны

### 6.1. Spring REST

- `parseJavaFile` рассматривает файл как контроллер только при наличии `@RestController` или `@Controller`.
- `extractClassRequestMapping` ищет ближайший к классу `@RequestMapping`.
- `extractRestMethods` по характерным Spring-аннотациям ищет методы и извлекает сигнатуру/тело с использованием `findBalancedClose` (балансирование скобок с учётом комментариев и строк).
- HTTP-методы: GET, POST, PUT, DELETE, PATCH; для `@RequestMapping` пробует прочитать `RequestMethod.X`, иначе допускает неизвестное значение `?`.
- Путь: `path`/`value` или первый позиционный аргумент аннотации; при массиве путей **берётся первый**, а не все варианты.
- `resolveExpr`/`resolvePlaceholders` разбирают строковые литералы, простую конкатенацию, Java-константы и `${key[:default]}`; рекурсивная подстановка ограничена глубиной 8. Неразрешённые фрагменты остаются видимыми и отмечаются `⚠️`.
- REST-контроллеры на интерфейсах, программные маршруты, нестандартные аннотации, наследование маппингов, варианты сгенерированных клиентов и тонкости Spring WebFlux могут не поддерживаться.

### 6.2. Параметры, DTO, JSON-примеры

- Парсер сигнатур определяет тип, имя и аннотации параметров; источники по `@PathVariable`, `@RequestParam`, `@RequestHeader`, `@RequestBody`, `@CookieValue`, `@ModelAttribute`.
- Некоторые инфраструктурные типы (`HttpServletRequest`, `Pageable`, `Authentication` и др.) скрываются из таблицы бизнес-параметров.
- `paramRequired` гарантированно помечает обязательным лишь `@PathVariable`; для прочих аннотаций не пытается выдавать настройки `required` за факт.
- `registerClasses` извлекает классы и `enum`; `parseDtoFields` — объявления полей верхнего уровня; `@JsonProperty` влияет на JSON-имя, `@JsonIgnore` убирает поле, `@NotNull/@NotEmpty/@NotBlank/@NonNull` дают признак обязательности, `@Schema`/`@ApiModelProperty` могут дать описание.
- `unwrapType` распаковывает характерные обёртки (`ResponseEntity`, `Optional`, `Mono`, `Flux`, `Result`, `ApiResponse`, пользовательские суффиксы `Response/Result/...`) и коллекции (`List`, `Set`, `Page`, `Slice`...).
- `dtoSchemaDeep` рекурсивно формирует табличное описание вложенных объектов (до глубины 5); `jsonExample` строит **синтетический** объект со стандартными значениями. `sampleObj` ограничен глубиной 6 и защищён от рекурсивных ссылок.
- Для классов из внешних библиотек или не включённых в индекс строится сообщение «структура типа не найдена»; `...` внутри JSON означает неизвестную структуру. Реальные правила Jackson-сериализации не моделируются полностью.

### 6.3. Описания методов и классов

Источники: Javadoc, Swagger/OpenAPI-аннотации (`@Operation`, `@Tag`, `@Schema` и др. в поддержанных местах) и эвристика `describeFromName`/`describeClassName` на основе Java-имён. Автоматически составленный текст обозначается как предположение. Это **не** семантическое понимание кода нейросетью.

### 6.4. Базы данных

- `registerClasses` распознаёт `@Entity`, `@Table(name/schema)`, некоторые `@Column` и выводит имена по `toSnake` при отсутствии аннотаций.
- `registerRepo` распознаёт интерфейсы `Repository`/`Dao`, родительские сущности, `@Query` с `nativeQuery` и JPQL в простых случаях.
- `registerMyBatisMapper` ищет аннотации `@Select/@Insert/@Update/@Delete`; **XML-мапперы MyBatis не разбираются как SQL-контракты**.
- `extractSqlTables` ищет таблицы в `FROM`, `JOIN`, `INTO`, `UPDATE`; `extractRawSqlTables` — ограниченные SQL-литералы внутри методов.
- `traceTouchpoints` собирает БД-затрагивания через поля зависимостей, репозитории, мапперы и найденные литералы SQL; различает условное «чтение/запись» по именам операций (`save`, `find`, `delete` и т. п.).
- `defaultSchema` ищет несколько типовых Hibernate/Datasource/Flyway/Liquibase-ключей, опциональный CSV/XLSX-каталог может уточнять схему и список колонок.
- `mappingHintsSection` строит **гипотезы** соответствия полей DTO и колонок затронутых таблиц по именам. Нельзя использовать эти гипотезы как подтверждённое фактическое отображение.
- Не гарантируются схемы и таблицы при сложных динамических запросах, аннотационных/ORM-соглашениях конкретной компании, вызовах через обёртки и в коде, который невозможно связать с найденной точкой входа.

### 6.5. Kafka, JMS/Artemis

- `collectMessaging` ищет типовые аннотации `@KafkaListener`, `@JmsListener`, вызовы `kafkaTemplate.send`, `streamBridge.send`, `jmsTemplate.send/convertAndSend` и схожие паттерны.
- `resolveAllMessaging` разрешает строковые значения/плейсхолдеры и строит связи producer/consumer по найденным именам каналов.
- Файлы отдельного топика/очереди описывают найденные события/отправителей/получателей, но **не являются runtime-трассировкой доставки**.
- Выборочные тесты на реальном репозитории показали, что некоторые топики находятся, но достоверность всех связей не проверена. Нестандартные обёртки, динамический выбор адресата и брокерная маршрутизация могут быть пропущены.

### 6.6. Шедулеры и отложенные задачи

- `@Scheduled` и некоторые выражения `fixedDelay/fixedRate/cron` — простыми шаблонами.
- Quartz: `registerQuartzConfig`, `collectQuartzJobs`, `quartzScheduleText` находят конфигурационные cron-выражения и классы `Job`/`QuartzJobBean` в узнаваемом виде.
- Собственные «task»-паттерны: `collectTaskSignals` и `buildTaskFeatures` связывают вероятные таблицы задач, классы-обработчики, статусы, настройки расписания; вывод оформляется в `задачи/*.md` и **носит гипотетический характер**.
- `collectDiagnostics` отдельно перечисляет технические механизмы, упоминания которых присутствуют в коде, но которым нет соответствующей полной логики анализатора. Наличие маркера не равнозначно корректному описанию выполнения.

### 6.7. Межсервисные вызовы и их главный предел

- `registerFeign` разбирает поддержанный вид `@FeignClient`, имя сервиса, базовый путь, аннотации методов клиента.
- `feignCallInfo` может связать вызов по полю-клиенту с описанием интерфейса Feign и вывести HTTP-метод/путь.
- `extractHttpClientCalls` пытается увидеть `RestTemplate`, `.uri(...)` WebClient, Apache HttpClient и OkHttp в типовых формах.
- `methodCalls` извлекает прямые вызовы на зависимостях контроллера.
- `indexClassMethods` + `resolveBean`/`ifaceImpl` + `traceTouchpoints` идут по известным реализациям и зависимостям до **трёх уровней вглубь** (`depth > 3` прерывает трассировку). Используются простые имена классов и методов; возможны коллизии, неоднозначные перегрузки, отсутствие реализации интерфейса, пропуски динамического диспетчинга.
- **НЕРЕШЕНО:** надёжно выйти из входного метода через внутренние обёртки/фасады проекта на вызываемый метод конкретного другого микросервиса и продолжить трассировку там. Feign-описания помогают в части случаев, но сквозная карта реальных вызовов между сервисами не построена. Длинный блок исходного кода или отметка «не распознано» — не свидетельство отсутствия вызова.

### 6.8. «Постановка наоборот» / каркас метода

- `responseCodesSection` читает явные `@ResponseStatus`, `@ApiResponse` и сигналы `throw`; **200 OK не подставляется без подтверждения в коде**.
- `algoSkeletonSteps` и `algoSkeletonSection` формируют предварительную последовательность по распознанным вызовам, условным веткам, БД, отправкам сообщений, возвратам/исключениям.
- `mappingHintsSection` выводит кандидатов соответствия DTO → БД, см. п. 6.4.
- Блок **«Когда вызывается»** намеренно оставлен аналитику: исходники не сообщают всех бизнес-сценариев, каналов и внешних инициаторов.
- **Каркас ≠ спецификация бизнес-логики.** Нет доказательства полноты ветвлений, транзакций, исключений, внешних контрактов и влияния side effects.

## 7. Формат выходных файлов

```text
Документация/
├── README.md                    # автосводка по выбранным модулям
├── _inventory.md                # перепись найденных модулей, ошибок, ограничений
├── _diagnostics.md              # диагностика распознанных/нерaспознанных паттернов
├── Карта репозитория.md         # общая обзорная карта
└── <группа>/<подгруппа>/<модуль>/
    ├── _index.md                # карточка модуля, API, архитектурный контекст
    ├── _database.md             # найденные связи с таблицами БД
    ├── методы/                   # отдельные страницы найденных REST endpoints
    │   └── 001_GET_<путь>.md
    ├── топики/                   # Kafka, если распознана
    ├── очереди/                  # JMS/Artemis, если распознаны
    ├── шедулеры/                 # @Scheduled/Quartz, если распознаны
    └── задачи/                   # отложенные задачи, если распознаны
```

Наличие папок `методы/`, `топики/`, `очереди/`, `шедулеры/`, `задачи/` условно: раздел создаётся только при наличии найденных объектов. Папка модуля повторяет структуру групп от выбранного корня; одинаковые короткие имена модулей в разных группах сохраняются раздельно.

### 7.1. Корневой `README.md` архива

Количество всех найденных и отобранных модулей, статистика контроллеров/endpoints, групповые таблицы, диагностика разрешения путей, общая таблица сообщений, объяснение условности описаний. **Не путать с `Analizator_repozitoriya_v1_0_README.md`** — отдельным файлом для блога.

### 7.2. `_inventory.md`

Число просмотренных папок и манифестов; таблица всех найденных модулей (в том числе невыбранных), их относительные пути и группы; манифесты без `src`; ошибки доступа и превышения глубины. Документ помогает сверить структурную полноту с реальным деревом исходников.

### 7.3. `_diagnostics.md`

Ошибки чтения файлов/каталогов; совпадения имён Java-классов; счётчики маркеров распознаваемых/пока не поддержанных механизмов; нестандартные аннотации; вероятные джобы; имена ключей конфигураций, похожих на расписания. Приводятся лишь ограниченные топы в некоторых разделах. Важное: **отсутствие предупреждений не означает полного корректного анализа**.

### 7.4. `Карта репозитория.md`

Общая таблица REST endpoints с привязкой к модулям, список найденных Kafka/JMS-каналов, шедулеров, отложенных задач и таблиц БД. Служит навигацией и точкой входа, не двусторонним графом всех реальных вызовов.

### 7.5. `_index.md` модуля

Местоположение и описание, число REST-методов, их перечень, оценочный архитектурный контекст (какие downstream-сервисы и таблицы удалось определить), Kafka/JMS, задачи/шедулеры. Внутренние связи могут быть неполными и требуют проверки.

### 7.6. `_database.md`

Таблицы, предположительные схемы и операции чтения/записи, найденные в доступной трассировке; при наличии каталога БД — известные поля; предположительные связи между сущностями/таблицами. Отсутствие строки не доказывает отсутствия работы с таблицей.

### 7.7. `методы/*.md`

Типовое содержимое:

1. Заголовок `HTTP_метод путь`, знак `⚠️` для частично разрешённых путей.
2. Описание метода (из аннотаций/Javadoc или предположение по имени).
3. Модуль, контроллер, исходный Java-путь, имя метода.
4. **«Когда вызывается»** — пустая заготовка для аналитика.
5. Параметры path/query/header/cookie/form (из сигнатуры и аннотаций).
6. Тело запроса и тип ответа: таблицы полей DTO, примеры **синтетического JSON**.
7. Коды ответа и обнаруженные исключения (без выдумывания 200 OK).
8. Каркас алгоритма (только признаки, доступные статическому анализу).
9. БД, предполагаемые DTO→колонки, обнаруженные вызовы сервисов и HTTP, публикации сообщений, прямые зависимости контроллера (при наличии).
10. Исходный код метода либо отметка, что он исключён пользователем (переключатель `includeSource`).

Для каждого блока должны сохраняться разделения **достоверно извлечённое из синтаксиса / догадка / неизвестно**; сообщения сканера часто подчёркивают необходимость проверки разработчиком.

## 8. Технический стек, приватность, ограничения среды

### 8.1. Стек и упаковка

- HTML + встроенные CSS и JavaScript; JSZip встроен прямо в документ, подключения CDN нет.
- `showDirectoryPicker`, файловые handle-объекты, `File.text()`/`File.arrayBuffer()`, Blob URL, стандартные API браузера.
- Нет backend-сервера и обработки на стороне сайта; сайт в футере — обычная ссылка, не цель передачи данных.
- Markdown формируется строковыми шаблонами и JSZip; файловая система репозитория не модифицируется.

### 8.2. Вопросы безопасности

- Сам HTML не отправляет считанные исходники во внешний сервис (нет механизма API/AI-вызова).
- **Сгенерированный ZIP потенциально содержит конфиденциальные данные**: исходники, внутренние адреса, SQL, схемы БД, топики, классы и сигнатуры. При включённом `includeSource` добавляются тела методов. При выключенном флажке другие чувствительные сведения остаются.
- Запрещено без разрешения загружать или публиковать полученный из рабочего корпоративного репозитория архив. Для публичных тестов использовать синтетические или разрешённые исходники.

### 8.3. Поддержка браузеров

Требуется File System Access API с `showDirectoryPicker` — в обычной практике **Chrome/Edge на Windows/macOS**, при допустимом для API контексте открытия HTML. Утверждение «любой современный браузер» было бы неточным. Порог памяти, количество файлов и права могут влиять на работу. Поддержка других браузеров не подтверждена.

### 8.4. Что с производительностью

Сканирование выполняет обход по дереву и чтение каждого выбранного Java-файла, а затем строит несколько индексов и большие Markdown-строки. В алгоритме предусмотрены периодические уступки UI, но обработка крупного монорепозитория может требовать значительного времени и оперативной памяти. Лимиты размера 1 МиБ присутствуют **в предварительном сборе конфигов/общих Java-файлов**, но обычный проход выбранного модуля зависит от того, что прочитает браузер. Нет гарантии работоспособности для любого размера проекта.

## 10. Качество результата и приёмка

### 10.1. Что действительно проверено

- В v0.25 исправлен рекурсивный поиск в многоуровневом репозитории: в синтетическом браузерном тесте найдены **87/87** модулей в группе `app`, **93** модуля в ZIP, **91** REST endpoint. Это проверка соответствующего тестового дерева, не полноты реальных проектов.
- Пользовательский прогон v0.25 показал **238 модулей, 482 контроллера, 1490 endpoints, 22754 Java-файла**; выборочный просмотр карты и отдельных методов дал положительную оценку структурной полезности.
- Полный аудит всех endpoints, HTTP-контрактов, таблиц, Kafka и сквозных внутренних вызовов **не проводился**.

### 10.2. Как интерпретировать качество

- **«Найден»** означает обнаружено правилом кода, а не доказано наличие/доступность в работающей системе.
- **«Не найден»** означает детектор не распознал подходящий фрагмент, а не что объекта/связи нет.
- **«Таблица/топик используется»** — след вывода по источникам, иногда косвенный.
- **«Пример JSON»** — типовой шаблон, не запись реального трафика.
- **«Описание по имени»** — гипотеза, не бизнес-требование.
- **«Код ответа»** — только явно обнаруженные признаки, не полный контракт.

> **Статус: отложено без плана работ.** Список ниже нужен для будущего автора или пользователя, который захочет адаптировать утилиту под собственный код. Финализация 1.0 **не** означает обязательства делать следующую версию.

- [ ] **Ограничение / ключевая нерешённая задача:** надёжно восстанавливать цепочку `REST endpoint → внутренние зависимости → клиент → конкретный метод другого микросервиса`, включая собственные обёртки, фасады, адаптеры и нестандартную маршрутизацию.
- [ ] **Ограничение:** повысить полноту определения REST endpoints для интерфейсных, унаследованных, нестандартно аннотированных и динамических маршрутов; корректно отражать несколько путей одной аннотации и разные HTTP-методы.
- [ ] **Ограничение:** обеспечить точность DTO/JSON на реальных кодовых базах с обобщёнными типами, наследованием, Lombok/Jackson и внешними библиотеками; заменить модель «синтетический пример» на подтверждённую схему, если будет такой источник.
- [ ] **Ограничение:** улучшить достоверность определения БД, в том числе динамических SQL, XML-мапперов MyBatis, собственных DAO-обёрток, JPA relationships, транзакций и фактического mapping.
- [ ] **Ограничение:** повысить полноту и точность Kafka/JMS/Quartz и собственных механизмов задач; разрешать реальные имена топиков, корректно понимать producer/consumer и условия запуска.
- [ ] **Технический долг:** построить глобальные индексы по полному квалифицированному имени (`package.Class`), а не по коротким именам; корректно учитывать перегрузки Java-методов.
- [ ] **Технический долг:** явная диагностика пропусков при сборе конфигураций/общих Java-файлов, отдельные лимиты глубины 30/48, контроль полных наборов исходников и больших файлов.
- [ ] **Тестирование:** набор разнообразных *разрешённых или синтетических* Java/Spring-репозиториев с известной эталонной документацией; измерение полноты, ложных связей, качества ZIP и стабильности на Windows/macOS.
- [ ] **Идея, не включена в 1.0:** локальный/внутренний API или необязательный AI-анализ документации с явной моделью доступа и соблюдением конфиденциальности. В текущем HTML **нет AI-подключения**.
- [ ] **Идея:** улучшенная навигация и верификация Markdown как основы живой базы знаний (ссылки на источники, уровень уверенности, ручное подтверждение человеком, обратная связь по покрытиям).
